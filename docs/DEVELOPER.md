# Connect: передача проекта

Connect продаёт SMS поверх платформы easysms. Клиент компании не ходит в easysms напрямую: он вызывает Connect, Connect проверяет свои правила и только потом отправляет сообщение поставщику.

Спецификация поставщика лежит в корне: `Интеграция API easysms_v3.docx`, редакция 2.01, API easysms/v3. Это источник правды по HTTP-контракту. Публичный сайт easysms.co и чужие REST-примеры к этому контракту не относятся.

## Границы

Деньги и отправка живут в одном месте — Go-шлюзе `services/gateway`.

- Кабинет (`apps/web`) пишет контакты, группы, подписи, шаблоны, профили, ключи и настройки своим SQL.
- Отправка, OTP, пополнение баланса и выпуск сообщения с модерации идут в шлюз. Кабинет вызывает его заголовками `X-Internal-Token` и `X-User-Id`, сырой ключ клиента при этом не нужен.
- Баланс меняет только шлюз. Второй писатель баланса сломает списания.

Схема базы одна. Её ведёт goose, файлы лежат в `services/gateway/internal/migrate/migrations`. Шлюз применяет их при старте. Prisma в проекте нет.

## Запуск

Postgres слушает хост-порт `5434`, потому что `5432` и `5433` на машине разработки уже были заняты.

```powershell
docker compose up -d postgres
cd services/gateway
go run ./cmd/seed
go run ./cmd/gateway
```

Во втором окне:

```powershell
cd apps/web
npm install
npm run dev
```

- Кабинет: http://localhost:3000
- REST: http://localhost:8080
- gRPC: `localhost:50051`, сервис `connect.v1.SmsGateway`, включена reflection
- Короткий адрес: `GET /s/{code}`

Демо-клиент: `demo@connect.local` / `demo12345`, ключ `cnt_demo_7f3a9c2e1b`, подпись `CONNECT` уже активна, баланс после сида `1500`.  
Администратор: `admin@connect.local` / `admin12345`.

`go run ./cmd/seed` идемпотентный: настройки и тарифы обновляет, демо-пользователей поднимает заново. Повторный запуск не должен плодить подписи и контакты.

## Секреты

`.env` в git не входит. Образец — `.env.example`. Кабинет читает `apps/web/.env`, шлюз читает `services/gateway/.env`, а если его нет — `../../.env`.

`SESSION_SECRET` подписывает куку `connect_session` на 7 дней. `INTERNAL_TOKEN` связывает кабинет и шлюз. Оба значения в бою нужно заменить.

Пока пусты `EASYSMS_LOGIN`, `EASYSMS_PASSWORD` или `EASYSMS_CONNECT_ID`, шлюз принудительно работает в макете и наружу не звонит. `EASYSMS_MOCK=true` делает то же самое даже при заполненных реквизитах. Адрес по умолчанию: `https://xml.smstec.ru`.

| Путь | Зачем |
| --- | --- |
| `apps/web/src/app` | Страницы кабинета и маршруты `/api` |
| `apps/web/src/lib/db.ts` | Пул `pg`. Ответ SQL переводится в camelCase |
| `services/gateway/cmd/gateway` | HTTP, gRPC, миграции, воркер |
| `services/gateway/cmd/seed` | Демо-данные |
| `services/gateway/internal/sms` | Правила отправки, очередь, OTP, вебхук |
| `services/gateway/internal/upstream` | Клиент easysms/v3 |
| `services/gateway/internal/store` | SQL. Таблица `groups` в запросах берётся в кавычки: это зарезервированное слово |
| `services/gateway/internal/policy` | Телефон, сегменты SMS, статусы, статусы easysms |
| `proto/connect/v1/gateway.proto` | Контракт gRPC |
| `services/gateway/gen` | Сгенерированный Go. В git не входит |

Файлы держатся маленькими: один файл — одна задача. Новый код лучше класть рядом, а не собирать заново большой `service.go`.

Сгенерировать gRPC локально, из корня репозитория:

```powershell
protoc -I proto --go_out=services/gateway --go_opt=module=github.com/connect/gateway --go-grpc_out=services/gateway --go-grpc_opt=module=github.com/connect/gateway proto/connect/v1/gateway.proto
```

Образ шлюза делает это сам. Плагины: `protoc-gen-go` v1.36.6 и `protoc-gen-go-grpc` v1.5.1. Модуль Go — `github.com/connect/gateway`.

Проверка шлюза: `go test ./...` в `services/gateway`. Проверка кабинета: `npx tsc --noEmit` в `apps/web`.

## Клиентский API

Авторизация REST: `Authorization: Bearer <ключ>` или Basic `email:ключ`. Ключ хранится как SHA-256 hex, одинаково в Go и в кабинете. Сырой ключ показывается один раз при создании.

gRPC читает метаданные `authorization`.

Кабинет для своих вызовов шлюза использует внутренний токен, не ключ клиента.

Основные маршруты: `/v2/sms/send`, `/v2/sms/status`, `/v2/sms/list`, `/v2/balance`, `/v2/balance/add`, `/v2/otp/create`, `/v2/otp/validate`, контакты, группы, подписи, чёрный список. Страница `/docs` в кабинете повторяет короткий пример.

Номер — цифры с кодом страны, без `+`, длина 10–15, без ведущего нуля. Текст не короче `min_text_length` (по умолчанию 4). Получателей не больше `max_receivers` (по умолчанию 1000).

## Отправка

`sms.Send` проверяет лимит (60 отправок в минуту на пользователя), текст, callback, подпись, чёрный список и баланс. Callback на localhost и частные адреса отклоняется.

Дальше три ветки:

1. Немедленная отправка. Сначала вызов easysms по одному получателю, затем запись и списание. Общий отказ поставщика — HTTP 502 и строки со статусом отклонения. Частичный успех — HTTP 200.
2. Отложенная или плавная отправка. Деньги списываются сразу, сообщения остаются `pending`. Воркер раз в 15 секунд забирает их через `FOR UPDATE SKIP LOCKED` и отправляет. Ошибка поставщика возвращает деньги.
3. Модерация договора. Включается настройкой `require_approved_contract`. Сообщение получает статус 8 и `upstream_state=held`, деньги не списываются. Администратор выпускает его через `POST /internal/messages/{id}/release`: тогда происходит списание и сообщение встаёт в очередь.

Цена клиента = тариф канала и оператора × `(1 + markup_percent/100)` × число сегментов. Сегменты: GSM 160/153, UCS-2 70/67. Каналы тарифа: `PAY_SIGN`, `FREE_SIGN`, `SERVICE`, `AUTH`. Оператор, если у контакта его нет, угадывается по российскому DEF-префиксу. Это локальная оценка, не HLR у оператора.

Подпись обязательна, пока `require_approved_sign` не выключен. В easysms она уходит полем `originator`. В текст она добавляется только при `prefix_sign_in_text=true`.

Статусы сообщения в кабинете и REST:

| Код | Смысл |
| --- | --- |
| 0 | очередь |
| 1 | доставлено |
| 2 | не доставлено |
| 3 | передано поставщику |
| 4 | ожидание |
| 6 | отклонено |
| 8 | модерация Connect |

## easysms/v3

Один метод:

`POST {EASYSMS_BASE_URL}/api/v3/easysms/{connect_id}/SendMessage`

Тело:

```json
{
  "Header": { "login": "...", "password": "..." },
  "Payload": {
    "message": {
      "client_message_id": "cmsg_...",
      "messenger_type": "sms",
      "originator": "CONNECT",
      "recipient": "79001001010",
      "text": "текст"
    }
  }
}
```

Получатель в одном запросе один. `client_message_id` уникален на нашей стороне и сохраняется в `messages.client_message_id`. Ответ поставщика содержит `message_id`, он пишется в `upstream_message_id`.

HTTP 403 — неверные реквизиты. Ошибка платформы приходит объектом `error` с `error_code` и `error_message` (например, 66 «номер запрещён», 65 «закончился баланс», 68 «имя не зарегистрировано»). Полный список кодов — в docx.

Статусы доставки поставщик сам присылает на `POST /easysms/v3/webhook`. Если задан `EASYSMS_WEBHOOK_TOKEN`, он должен совпасть с `Header.token`. Иначе вебхук принимается без секрета: так выглядит пример в спецификации.

Коды easysms, которые мы записываем:

| Код | Что делаем |
| --- | --- |
| 102, 106 | доставлено |
| 103, 104, 105, 107 | не доставлено |
| 108 | отклонено |

Повторная недоставка уже оплаченного сообщения деньги сама не возвращает. Возврат есть, если поставщик отказал в момент отправки из очереди.

Для боевого подключения службе easysms нужно сообщить IP, с которого пойдут запросы, и получить логин, пароль, `connect_id` и зарегистрированные имена отправителя. Имена в кабинете — наша модерация; поставщик всё равно отклонит незарегистрированное у него имя.

## OTP

Отдельных методов create/validate у easysms/v3 нет. OTP — это `messenger_type=flash_call`: в запросе нет подписи и текста. Код (последние цифры номера звонящего) приходит вебхуком в поле `code` и сохраняется как SHA-256. `POST /v2/otp/validate` сравнивает код локально. Пока вебхук не пришёл, проверка отвечает «код ещё не получен».

В макете код из шести цифр создаётся сразу. При `MOCK_REVEAL_OTP=true` он попадает в ответ create, чтобы можно было проверить validate без звонка.

## Кабинет

Next.js 15, React 19, TypeScript. Белые страницы, розовый акцент `#ff4b7d`, зелёные кнопки действий. Разделы: Рассылки, Контакты, Подписи, Статистика, Счета, Акции, Настройки.

Пополнение меняет внутренний журнал. Номер карты целиком не хранится, только бренд и последние 4 цифры. Промокод `CONNECT10` и автоскидка 10% от 3000 ₽ не складываются.

Контакты можно импортировать текстом или файлом csv/txt/xlsx. HLR в интерфейсе заново проставляет оператора по DEF-префиксу.

amoCRM и виджеты в настройках — честная заглушка, интеграции нет.

Юридические тексты, телефон и почту чужого кабинета не копировать. Подвал и формулировки Connect свои.

## Что проверить после правок

Кабинет: вход демо-пользователем, список контактов, рассылка на группу «Клиенты» с подписью `CONNECT`, обновление баланса. В макете два сообщения должны получить статус «передано», а в базе — свои `client_message_id`.

REST: `POST /v2/sms/send` с ключом `cnt_demo_7f3a9c2e1b`.

Вебхук можно подать вручную на `/easysms/v3/webhook` с `client_message_id` уже отправленного сообщения и `state` `102`. Статус в кабинете должен стать «доставлено».
